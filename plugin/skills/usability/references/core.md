# Usability: task flow, interaction, forms, status, errors, search, efficiency

Platform-agnostic. See `../shared/evidence-model.md` and `severity-model.md` for how to report findings from these rules. Platform-specific (iOS/Android) usability rules live in `mobile.md`.

| A14R | A disabled/grayed-out control explains, when the user directly interacts with it (clicks, taps, or focuses it), why it is currently unavailable and what specific step would enable it; silent graying-out with no explanation on interaction is insufficient. Distinct from A01R, which governs a single screen's primary-vs-secondary hierarchy, not variant count across the product, and from A13R, which governs a single control's label matching its own destination, not stylistic consistency across controls. | Strong | Moderate | Herbert Bayer, Universal Typeface (systemic variant reduction); Stockholm Design Lab, Askul packaging system (via Sean Adams, *How Design Makes Us Think and Feel and Do Things*) |

### Confirmation-dialogue simplification technique

When an A05R or A06R finding flags a confirmation dialog whose title, body copy, and button labels are misaligned, apply this refinement sequence rather than editing the wording ad hoc:

1. **Extract the discrete facts** the dialog currently states (what will happen, what conditions apply, what is reversible or not).
2. **Prioritize destructive/irreversible consequences first** — move the most consequential fact to the top; secondary details follow.
3. **Phrase the title as a direct question** rather than a statement or label (for example "Limit sharing to domain users?" instead of "Sharing settings").
4. **Align the button labels to literally answer that question** (for example "Yes"/"No") instead of generic or jargon verbs ("Enable"/"Cancel") that do not restate the question's answer.
5. **Strip jargon and redundant technical explanation** the buttons or title already made clear.

This is a technique for satisfying A05R (specific, consequence-naming confirmation) and A06R (outcome-stating choices), not a separate rule competing with them — a dialog can fail A05R/A06R without this sequence being the right fix (for example if the real problem is that no confirmation was needed at all, per A04R).

## Folk-rule guards

These are the exact kinds of oversimplified rules a review is likely to hallucinate as absolutes unless explicitly constrained. Apply the "better encoding" instead of the folk rule.

| Folk rule | Better encoding |
|---|---|
| "Never use a hamburger menu." | Penalize hidden **primary/high-frequency** navigation when discoverability matters; allow it for secondary/large sets of destinations (see N06R). |
| "All primary actions must be at the bottom because of the thumb zone." | Consider reachability and frequency, but do not assume a single grip; thumb-zone reasoning is a heuristic, not a layout law (see `mobile.md` T07). |
| "Always show onboarding." | Default to no standalone onboarding; require it only when setup, unfamiliar mechanics, safety, or unavoidable conceptual complexity justify it (product-lens concern, see `product` skill). A modal instruction pop-up is a particularly weak substitute: an eye-tracking study of a tablet app found most users dismissed an instructional pop-up in well under a second of fixation, and all subsequently failed the custom-gesture task it was meant to teach (Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design*, 2014). |
| "Always confirm delete." | Prefer undo for routine reversible deletion (A04R); confirm serious, unusual, irreversible, expensive, or security-sensitive actions (A05R, and trust-lens destructive-action rules). |
| "Never use dialogs." | Use dialogs for truly interruptive, narrowly scoped tasks or critical decisions; avoid them for ordinary informational feedback (A07R). |
| "Always use a skeleton instead of a spinner." | Show useful structure/content early when it improves comprehension (S03); use determinate/indeterminate progress according to what is actually known (S04). |
| "Bottom navigation must always have exactly N items." | Use platform-specific guidance — see `mobile.md` N03R for Android's 3-5 destination target; iOS guidance focuses on top-level navigation semantics, not a fixed count. |
| "Disabled buttons are bad." | A disabled state can be valid, but prerequisites must be understandable and users must not be trapped without explanation (A08R). |
| "Swipe actions are bad." | Swipe can be an efficient shortcut for contextual actions, but must stay consistent, discoverable, and not the only access path to important functionality (see `mobile.md` T06). |
| "Animations are bad/good." | Motion must communicate state or continuity, remain responsive, and respect reduced-motion settings; decorative motion should not impede tasks. |
| "More steps are always worse." | A short staged flow can reduce complexity and errors; the cost depends on dependency between steps, frequency, and information needed for decisions (see `product` skill P03). |
| "Miller's Law means navigation/menus must cap out at 7 (or 5) visible items." | Miller's Law describes active working-memory retention (holding items in mind without looking), not recognition of options that stay visible on screen — it does not set a maximum count for always-visible navigation or menus. Apply semantic chunking instead (see `psychology` skill PC07), and only reduce the number of choices when decision complexity actually warrants it (Hick's Law, see this file's Actions/Forms sections and the `product` skill). |

## How the usability skill should apply these

Start from the primary task (handed off from, or checked alongside, the `product` lens), then work through state-completeness (System status, Errors & recovery — is every state in `evidence-model.md`'s sense actually shown or knowably absent?), then interaction efficiency (does every explicit user intent get continued without redundant taps?), then the folk-rule guard table before finalizing any finding that resembles a popular "always/never" rule. When the evidence includes a form, also check the layout-ergonomics rules (F13-F17: button alignment, label proximity, sample-data contamination, single-column question layout, cross-step memory), the control-type rules (F18: no dropdown/select misuse for open-ended, high-cardinality data; F20: no dropdown misuse the other direction — a small, already-fixed option set hidden when it should be shown as visible radio buttons/checkboxes), the positive-feedback rule (F19: immediate confirmation on valid input, not only errors on failure), the defaults/memory rule (F21: dominant-value pre-selection and cross-session choice memory), and the field-grouping rule (F22: logical mental-model grouping, not alphabetical order). When it includes navigation menus, a dropdown/mega-menu, a list of options to compare, a post-authentication redirect, a deep-hierarchy page, or body content that mentions a related item, check N13R-N18R and D06 alongside the rest of Navigation and Search/discovery — N15R (redirect returns to prior context), N16R (breadcrumbs/footer sitemap), and N18R (contextual inline links at the point of reading) are new alongside the existing set. Check every control's actual effect against its label/appearance (A09R), every blocking modal against whether it forces an unrelated secondary action (A10R), any persistent/sticky mode against whether it is continuously visible (A11R), and any reused icon/signifier near a different, higher-consequence action against A12R, as part of the Actions pass, alongside A01R-A08R. Also check whether a control's label matches its destination's own heading word-for-word (A13R), whether a disabled control explains itself when interacted with rather than staying silently grayed out (A14R), whether a destructive control keeps adequate physical spacing from an adjacent safe control (A16R) — this is additive to `accessibility`'s T01/T02 target-size contracts, not a replacement for them — and, when the evidence spans more than one screen of the same product, whether functionally-equivalent controls (the same semantic action, such as a primary submit) render with a consistent, deliberate set of styles rather than unconstrained per-screen variation (A17R); a single-screen evidence set cannot support an A17R finding either way and should be reported `NOT ASSESSABLE`. When the evidence shows a scoping or containment default (for example a post's audience) established on one device, also check N17R against its mobile/desktop or cross-viewport counterpart. When the evidence includes a navigation structure, also check N19R: is every capability actually reachable within a reasonable discovery/interaction threshold, or does reaching it require external documentation or excessive nested navigation? Check top-level categories against N20R (could a user plausibly place the same item under more than one category?), N21R (does any label function as a vague catch-all dumping ground rather than a specific, descriptive category?), and N22R (do sibling items mix a sea-level task with a fish-level micro-action, rather than staying at a consistent goal-altitude?) alongside the rest of Navigation. When the evidence shows a persistent navigation or menu with a current-location indicator, also check N24R: does the active item use multiple simultaneous visual cues, or only one subtle attribute a scanning user could miss? When the evidence includes a search or discovery flow, check D07 (query/context preservation across a non-linear session), D08 (faceted filters prevent zero-result dead ends and offer a one-click clear-all control), and D09 (the search box itself is unscoped and clearly labeled before first use) alongside the rest of Search, discovery & comparison. When a list/collection view is evaluated, also check IE13 (bulk actions) and IE14 (background automation must not seize focus or interrupt active input) alongside the rest of Interaction efficiency. When the evidence shows any non-form status, confirmation, or error feedback, check S11 for focus-of-attention placement — F07 remains the rule for form-field validation feedback specifically. When the evidence shows a control whose real-world effect is not immediate (a temperature/climate setting, a background sync or processing toggle), check S12: does the interface expose the expected rate or remaining delay, or does its absence risk users pushing the control to an extreme value? When the evidence shows a wait or queue experience (checkout/processing, matchmaking, a support-ticket queue, an onboarding delay), check S13: is there a conservative duration/position estimate, is the user kept occupied rather than facing a static/empty state, is the queue order visibly fair, and does the wait end on a clear resolution? When the evidence shows an emergency, safety-critical, or acutely time-pressured flow, check CR01: does completing the primary response require only one prominent, immediately actionable control, or does it demand multi-step reasoning or dense reading at the worst possible moment? CR01 does not apply to calm, non-urgent flows. When the evidence includes a long, sequential, high-consequence procedure prone to memory failure under stress or interruption, check E09: is there an interactive checklist with persistent state that surfaces skipped steps, rather than reliance on memory of an implicit sequence? When the evidence includes a long numeric identifier the user must read or transcribe, check F23 for chunked formatting. When a form field asks the user to manually supply or select a value the system could instead derive from other input already given (e.g. a card-type selector alongside a card-number field), check F25. When the evidence includes a multi-step wizard or flow, also check N23R alongside N16R: is the total or expected remaining-step count shown, or an explicit not-yet-knowable signal, not only a trail of completed steps? When a finding could be explained by either a genuine usability defect or a legitimate contextual exception (progressive disclosure, secondary navigation, a deliberately browse-first search state), report it with the appropriate `evidence-model.md` status and name the exception condition rather than asserting a defect outright. When an A05R/A06R finding involves a confirmation dialog whose title, body, and buttons are misaligned, recommend the Confirmation-dialogue simplification technique (in this file's Actions section) as the concrete fix rather than a generic "make this clearer" recommendation. F26 treats field width as a format cue: compare each field's width with the length of the value it expects, and report widths the evidence does not show as `NOT ASSESSABLE`.

Check R07R whenever the evidence shows custom animation or transitions: is the motion purposeful, brief and skippable, or decorative and blocking? Check D10 for any long list or product grid that loads on scroll, and D11 for any review section. Static evidence cannot show duration or loading behaviour; report those parts `NOT ASSESSABLE`.
