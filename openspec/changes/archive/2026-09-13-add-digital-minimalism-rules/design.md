## Context

See `proposal.md` for motivation. Five content edits land across three already-existing reference files: `src/skills/product/references/core.md`, `src/skills/trust/references/mobile.md` (two edits), and `src/skills/psychology/references/{social.md,habits.md}`. None requires a new skill, a new reference file, or a change to `src/shared/*`. `product/core.md` uses `P0x` for purpose & task; `trust/mobile.md` uses `O0x` for permission/notification timing and `I0x` for interruptions; `psychology/social.md` uses `PT0x`. New rule content takes the next unused ID in the relevant scheme, consistent with the `IA01`/`IA02`, `E08`, and `PA09` precedent from prior book-comparison changes.

## Goals / Non-Goals

**Goals:**
- Close the five narrow, verified gaps identified during the *Digital Minimalism* comparison pass, each attributed to a named, independently checkable primary source (the Fogg Behavior Model / Apple & Android permission-justification guidance, Apple Focus / Android Do Not Disturb, Apple HIG's badge semantics plus published color-arousal/urgency-perception research, Sherry Turkle/MIT) — never to the book itself.
- Preserve the one-rule-ID-to-exactly-one-destination-file invariant: no rule ID duplicated or split across domains.
- Keep `product`, `trust`, and `psychology` model-invocable with no change to that default.

**Non-Goals:**
- No wholesale import of the book's remaining ~20 extracted items (attention-economy history, the 30-day digital declutter process, solitude/default-mode-network philosophy, single-purpose computing at the OS/workspace level, slow-media curation, community/event-organizing patterns, the Bennett active-vs-passive-leisure principle). Each is either the author's own unattributed framework, platform/OS-level guidance outside this project's screen/flow-review scope, or — for variable rewards, streaks, autoplay, and stopping cues specifically — already covered by this project's existing `PH02`-`PH04` and the `ethics.md` four-gate test, so re-adding them would duplicate rule IDs rather than close a gap. All stay deferred per `openspec/config.yaml`.
- No new skill, no new reference file (e.g. no `web.md`), no change to `src/shared/evidence-model.md`, `severity-model.md`, or `report-contract.md`.
- No change to `usability`, `accessibility`, or `review`.

## Decisions

1. **Feature/permission justification becomes a new `P08` in `product/core.md`, not a rewrite of `P06`.** `P06` already checks one narrow case (registration/personal data before value). The new rule generalizes the same underlying concern (a flow's benefit must be concrete and bounded) to any feature or permission request, including ones that never touch identity/data — a distinct, separately testable failure mode. Alternative considered: folding this into `P06`'s text — rejected because `P06`'s existing scenarios are specifically about registration/login gating and broadening its text would blur that finding's evidence requirements.
2. **Notification granularity becomes a new `O11` in `trust/mobile.md`, not an edit to `O09`.** `O09` already establishes "users can manage notification categories/preferences." Time-based quiet hours and sender-level allowlisting are an additional, independently checkable dimension (a product can pass `O09` with category toggles alone and still fail this one) rather than a citation-level refinement of the same claim — so this follows the `PA09`/`E08` "genuinely new failure mode" precedent, not the `V02` "citation addition to an existing rule" precedent.
3. **Badge/indicator urgency-color match becomes a new `I06` in `trust/mobile.md`'s Interruptions section, not a new rule in `attention.md`.** The failure mode is specifically an OS-level app-icon/notification badge — squarely `trust/mobile.md`'s existing remit (`O08`-`O10`, `I01`-`I05` already cover notification timing, honesty, and channel choice) — rather than `attention.md`'s in-screen Gestalt/visual-hierarchy concern. Keeping it in the same file as `I02` (interruption channel must match urgency) also keeps the two "does the visual/channel treatment match actual urgency" checks adjacent and mutually reinforcing.
4. **Conversation-channel bandwidth becomes a new `PT07` in `psychology/social.md`.** `social.md`'s existing `PT01`-`PT06` cover trust/predictability signals; this is a distinct concern (interaction richness for relationship-maintenance use cases) that the file's own scope statement ("psychological, interpersonal side of trust") already anticipates without prior rule content, matching how `product/core.md` got its `IA0x` prefix for a distinct-but-related concern in a prior change.
5. **Mobile severity calibration is an application-note addition to `habits.md`'s "How the psychology skill should apply these" section, not a new `PHx` rule ID.** It does not describe a new failure mode — it recalibrates how severity is assigned to the *existing* `PH02`-`PH04` findings based on platform context. This mirrors the precedent's `V02`-sample-size treatment (a citation/parameter-level addition to an existing rule) rather than a `PA09`-style new ID, and stays inside the severity bands already defined in `src/shared/severity-model.md` rather than inventing a parallel scale, per `openspec/config.yaml`'s spec rule against a parallel evidence/severity vocabulary.
6. **Sources cite the primary authors/orgs, never Cal Newport or "Digital Minimalism."** Per `openspec/config.yaml`'s standing rule, every new rule cites its independently verifiable primary source directly: the Fogg Behavior Model and Apple/Android permission-justification guidance for `P08`; Apple Focus / Android Do Not Disturb + priority senders for `O11`; Apple HIG's badge-semantics guidance together with published color-arousal/urgency-perception research for `I06` (a well-known industry anecdote about a major platform's red-vs-blue badge test may appear only as a "useful example," mirroring how `attention.md`'s `PA09` uses an illustrative example alongside its real NN/g sourcing); Sherry Turkle (MIT) for `PT07`.
7. **The mobile-severity note does not change `src/shared/severity-model.md`'s levels or add a platform axis to the shared model.** It is scoped to how the *psychology* skill applies the existing bands to a specific class of finding (engagement loops), consistent with `severity-model.md`'s own framing that severity is assigned per finding using judgment, not a formula — avoiding a project-wide precedent that every skill must now branch on platform.

## Risks / Trade-offs

- **[Risk]** `P08` and the existing `P06` could both fire on the same registration-before-value screen, producing an apparent duplicate finding. → **Mitigation**: `P08`'s scenarios and the "how to apply" text explicitly frame it as covering flows `P06` does not (permissions and features with no identity/data component); a reviewer citing both on the same screen should distinguish "value/justification is vague" (`P08`) from "value is gated behind registration" (`P06`) as two different observations, not report the same fact twice.
- **[Risk]** `O11`'s sender/contact-level allowlisting check could be reported as failing for products with no per-contact notion at all (e.g. a single-purpose utility app), inflating findings. → **Mitigation**: the spec's `NOT ASSESSABLE` scenario and the "how to apply" text gate this on notifications being "material to the product," matching the existing `O09` framing, and note that sender-level allowlisting is only applicable where the product has a notion of distinct senders/contacts.
- **[Risk]** `I06` (badge urgency-color) could be over-applied to any warm-colored badge, treating color choice as inherently suspect. → **Mitigation**: the requirement's text and scenarios anchor the check on a *mismatch* between visual urgency and actual criticality, not on the presence of red per se — a badge on a genuinely critical/safety flow using the same color is explicitly a pass.
- **[Risk]** `PT07` could be read as telling products to discourage async messaging generally. → **Mitigation**: the requirement and its logistics-only scenario make clear it applies only to relationship-maintenance framing, not to logistics, task coordination, or utility messaging.
- **[Trade-off]** Bundling five edits across three skills into one change (rather than one change per skill) keeps a single coherent research-comparison-pass proposal/design/spec set, at the cost of a slightly less atomic review than a three-way split would give — consistent with how the prior `add-ux-team-of-one-rules` change bundled two files under one proposal for the same reason.

## Migration Plan

Content-only change to Markdown source; no data migration. Rollout is: edit `src/skills/**` → `npm run build` (regenerates `skills/` and `plugin/skills/`) → `npm run sync-version` → `npm run validate`. Rollback is a plain revert of the same commit(s); no runtime state to unwind.
