## Goals / Non-Goals

**Goals:**
- Add the eight new rules and the citation-only enrichments identified in `proposal.md`, each traceable to a specific chapter/case in Don Norman's *Design for a Better World*.
- Keep every addition inside an existing reference file, consistent with this being additive content to established sections rather than new structure.

**Non-Goals:**
- No wholesale import of the book's physical-product circular-economy content, its ecosystem/decades-scale Humanity-Centered Design thesis, its Agile/Incremental-Modular-Design team-process content, or its Goodhart's-Law/proxy-metrics content — see `proposal.md`'s "Scoped out" section.
- No new reference file and no new skill — every addition fits an existing file's established scope.
- No change to the evidence/severity model, report contract, or any skill's model-invocability.

## Decisions

**The crisis/high-stress interaction rule lands in `usability/references/core.md`, not `psychology/references/emotion.md`.** Both files were considered. `emotion.md` covers psychological mechanisms and their ethical use (Peak-End, processing fluency, positive reinforcement) — it is about *interpreting* emotional/psychological effects. The new rule is an interaction-design mechanic (collapse the primary response to one prominent, immediately actionable control) closer in kind to `core.md`'s existing Actions and confirmation-dialog rules than to a psychological mechanism requiring the four-gate ethical test. It does not need an ethics-gate pass — it is a corrective usability rule, not a persuasive mechanism — so it belongs with usability's other corrective interaction rules.

**The semi-automation complacency-trap rule lands in `product/references/core.md`, not `psychology` or a new file.** The existing `usability` requirement on background automation (IE14) addresses interruption during active use, a different mechanism. `psychology`'s files are about persuasive/motivational mechanisms subject to the four-gate ethical test; the complacency trap is not a persuasive mechanism at all — it is a structural design defect in how a feature's automation/human-handoff boundary is designed, closer to `product`'s existing purpose-and-task-model rules (P01-P09) that judge whether a feature's design actually serves its stated function. A new file was considered and rejected: this is one rule, not enough surface area to justify a new reference file, consistent with how this project only splits out a new file for a genuinely new modality or a large enough topic cluster (see `usability/references/voice.md`'s precedent).

**The single-aggregate-number-fallacy and narrative-grounding rules both land in `product/references/core.md`'s Content section as new `C`-series rules, not as extensions of `C20`/`C21`/`C22`.** Each is a genuinely distinct, independently testable concern from the existing dashboard/chart/content-credibility rules already in that section (see `proposal.md`'s distinctions), so they are additive sibling rules rather than `MODIFIED` extensions, matching how this project has always added a new `C`-ID for a genuinely new concern rather than overloading an existing rule's text.

**The societal-affordance rule extends `usability/references/affordances.md`'s AF-series (a new AF-ID) rather than becoming a fifth affordance "type" folded into `AF01`'s existing four-type table.** Hartson & Pyla's four affordance types (Cognitive, Physical, Sensory, Functional) are a specific, cited framework from a specific source; Norman's societal-vs-physical-affordance distinction is a different source's framework describing a genuinely different axis (convention-based permission, not perceptibility or capability). Keeping it as a separate rule (rather than silently adding a fifth row to `AF01`'s table) preserves each framework's attribution and avoids implying Hartson & Pyla's model has five types when their own source names four.

**The invisible-prevention/safety-success-backlash rule lands in `trust/references/core.md`, parallel to the existing `PR01` post-interaction-reassurance rule, rather than in `usability`'s System status section.** Both are about communicating system activity the user cannot otherwise perceive, but `PR01` and this new rule are specifically about *trust erosion* from an absence of communication (users disable protection, or doubt a transaction completed) rather than *task-completion feedback* (the concern `usability`'s S01-S11 rules address). This matches the existing split: `usability` owns general state-completeness feedback, `trust` owns feedback whose absence specifically damages the user's trust in or willingness to keep using a protective/committing mechanism.

**The Legacy Assumption Audit is added as a named technique in `review/references/review-model.md`, referenced from the existing `V06` "name a concrete technique" requirement, not as a new numbered rule (`V08`).** This follows the exact precedent of the existing Role-Play UI Audit: a technique description in prose, with a corresponding `ADDED` spec requirement describing when the review skill may recommend it, rather than a new `V`-series validation-methodology rule (those describe standing constraints on every report, not one specific technique among several available options).

## Risks / Trade-offs

- **The crisis/high-stress interaction rule could be over-applied to any flow with a warning or alert, diluting its intent.** Mitigation: the rule text and the spec scenario both require the flow to be "explicitly framed as an emergency, safety, or acute time-pressure response" — a routine confirmation dialog or a non-urgent warning does not qualify, and the rule explicitly states it does not apply to calm, non-urgent flows.
- **The semi-automation complacency-trap rule could be read as opposing all semi-automation, when the book's own point is narrower (the specific passive-monitoring handoff pattern).** Mitigation: the rule and its spec scenario are scoped to the specific failure (no advance lead time before a handoff at the moment of failure), with an explicit passing scenario for active-engagement designs, so a well-designed semi-autonomous feature with periodic checkpoints is not penalized.
- **Adding a fourth new `product` rule and a third new `usability` rule in one pass is more additions to two files than several recent passes.** Mitigation: each was checked individually for genuine non-overlap with every existing rule in its target file (see `proposal.md`'s explicit distinctions from `C20`/`C21`/`C22`, `S01`/`S04`, and `IE14`) before being included, consistent with this project's standing bar for inclusion — this is a byproduct of the source book's specific chapter-by-chapter breadth, not a relaxed bar.

## Migration Plan

Standard content-change flow already used by every prior comparison pass: implement source edits (`src/skills/**`, no new files), run `npm run build && npm run sync-version && npm run validate`, update `CHANGELOG.md` and README's "Evidence base" plus the rule-count line, then archive. No data migration, no runtime deployment step, no rollback beyond reverting the commit.
