## Context

See `proposal.md` — Why. This is this project's tenth named-source comparison pass (after Writing Is Designing, eye-tracking research, Digital Minimalism, a UX-team-of-one practice book, White Hat UX, Understanding Context, The Elements of User Experience, Laws of UX, and The UX Book — see `CHANGELOG.md` 0.1.6-0.1.14). The source is Jesmond Allen & James Chudley's *Smashing UX Design: Foundations for Designing Online User Experiences*, whose extracted 24-item knowledge map (plus its process/methodology chapters) was compared item-by-item against every existing rule in `src/skills/*/references/*.md` before this proposal was drafted, confirming five items already covered: workarounds/cheatsheets as a usability-failure signal (`usability` `AF02`), forced-registration-before-checkout avoidance (`product` `P06` + `trust` `O11`), in-context help over isolated FAQ portals (`product` `C06`), form-as-polite-conversation minimalism (`usability` `F02`/`F07`/`F14`), and no-app-install-wall/touch-target requirements (`trust` `O15` + `accessibility` `T01`/`T02`).

## Goals / Non-Goals

**Goals:**
- Add the specific, checkable, independently-namable rules the book contributes that no existing rule already covers: L.A.T.C.H.-based content organization, mutually-exclusive top-level navigation categories, a catch-all-navigation-bucket ban, content-vs-ornamental photography, a data-table/dashboard audience-fit check, faceted-filter dead-end prevention, and mobile device-capability form input.
- Give the book's Expert Review two-pass discipline (persona-driven Cognitive Walkthrough, then Heuristic Evaluation) an explicit home in `review/references/review-model.md`'s Validation methodology, since — unlike the book's other process content — this item describes how the review activity itself should be structured, per explicit owner decision to include it.
- Enrich two existing rules' citations (`product` `C05`, `usability` `L07`) with Giles Colborne's localization-predictability hierarchy as the named rationale for why translation/culture is the least predictable layer, without changing either rule's behavior or adding a new rule ID.
- Keep every addition mapped to the three existing skills touched (`product`, `usability`, `review`) — no new skill, no new top-level lens, no new reference file.

**Non-Goals:**
- Importing the book's process/methodology content — the Virtuous Circle of iterative UCD, Agile Sprint-Zero modeling, developers observing usability-test sessions, analytics-as-"what"-vs-qualitative-research-as-"why", search-log mining as an IA-research technique, wireframe data-consistency as a testing-validity concern, and severity-rated-annotated-screenshot report formatting. These describe how a UX team runs its own research/design process or formats its own deliverables, not what a static-evidence review checks, consistent with every prior comparison pass's treatment of process content.
- Importing the book's e-commerce-specific cart/checkout vertical (cart-as-shortlist, non-expiring cart persistence) — deferred consistent with the 0.1.9 and 0.1.11 passes' identical treatment of e-commerce-vertical content.
- Adding the book's Rule of Odds (3-or-5-item product-grid rows) as a rule. It is an uncited visual-composition folk claim with no independent, verifiable research source — the same evidentiary gap that led the 0.1.6 pass to debunk the unsourced "Miller's Law caps navigation at 7" claim rather than encode it. Per explicit owner decision, this stays excluded and is not added to the Folk-rule guards table either, since the book asserts it as its own guidance rather than as a myth this project needs to actively debunk for users.
- Re-deriving rules already covered under different names: workarounds/cheatsheets, forced-registration avoidance, in-context help, form-as-conversation minimalism, and no-app-install-walls/touch-targets are confirmed already covered and left untouched.
- A new reference file for the data-table/dashboard content ("expert knowledge trap"). Unlike `affordances.md` or `visual-hierarchy.md`, which each anchor multiple rules and an independent diagnostic vocabulary, this book contributes exactly one checkable rule (`C20`) on this topic — not enough independent conceptual weight to justify a new file per this project's established file-growth precedent (`voice-tone.md` and `visual-hierarchy.md` were each seeded with several rules at once). `C20` is added to `product/references/core.md`'s existing Content table instead.
- Reworking `review/references/review-model.md`'s existing lens-selection procedure or `V01`-`V06` validation methodology structure. `V07` is added as an additional named rule in the Validation methodology section, not a restructuring of the existing four-step lens-selection procedure.

## Decisions

**`IA09` (L.A.T.C.H.) lands in `product/references/information-architecture.md`, not `usability`.** It is a content-organization/IA concern — which sort and filter modes a collection of content offers — squarely inside the file's existing three-materials framing (labels/ontology, relationships/taxonomy, rules/choreography) and alongside `IA06`'s structural-topology rule, which it is explicitly distinguished from in its own requirement text (topology vs. sort/filter mode are different questions about the same IA).

**`C19` and `C20` both land in `product/references/core.md`'s existing Content table, not a new file.** Both are content-quality concerns of the same shape as the file's existing `C01`-`C18` rules (is this content serving the user's actual need, per the file's stated "content quality is judged by whether it serves the goal" principle) rather than a structural framework with independent conceptual weight. This keeps the one-new-file-per-multi-rule-topic precedent intact (see the Non-Goals entry above) while still giving each its own rule ID per this project's one-rule-ID-to-one-mechanism convention.

**`N20R` and `N21R` are two separate rule IDs, not one combined rule.** Mutual exclusivity (can an item be placed under more than one category?) and catch-all-bucket avoidance (does a vague label exist as a content dump?) are related but independently checkable failure modes — a navigation structure can have perfectly exclusive categories and still contain a "Resources" catch-all, or vice versa — so each gets its own scenario set and rule ID, consistent with this project's established one-rule-ID-to-one-mechanism pattern (see `N15R`-`N19R`, each its own requirement).

**`D08` sharpens `D04`/`D05` rather than replacing either.** `D04` governs what a no-results page communicates once a dead end is reached; `D05` governs whether currently-applied filters are visible. Neither requires the *prevention* mechanism (dynamically hiding/disabling zero-count options before selection) or the *escape* mechanism (a one-click clear-all control) that `D08` adds — a faceted UI could pass both `D04` and `D05` (clear no-results messaging, visible filter chips) while still trapping users in a dead end with no fast way out, which is exactly the gap `D08` closes.

**`F24` lands in `usability/references/mobile.md` under a new "Forms (platform contracts)" section, continuing the existing `F`-prefix rather than starting a new one.** This mirrors the established precedent of `N02R`-`N05R`/`N10R`-`N12R` living in `mobile.md` while continuing `core.md`'s `N`-series numbering — a single logical rule-ID sequence split across a platform-agnostic file and a platform-specific addendum. `F24` is genuinely platform-specific (camera/geolocation/OS payment-sheet APIs are device capabilities, not a platform-agnostic UX principle), which is exactly the bar `mobile.md`'s own intro sets for addendum content.

**`V07` (the Cognitive-Walkthrough-then-Heuristic-Evaluation sequence) lands in `review/references/review-model.md`'s Validation methodology alongside `V01`-`V06`, not inside any single domain skill.** Like `V01`-`V06`, it is a cross-lens methodology concern about how the review activity itself should proceed, not a domain-specific content rule — the same reasoning that already put `IC01` (Interaction Cycle root-cause classification, from the prior UX-Book pass) in this file rather than in `usability`. Framed as `V07` (continuing the `V`-series) rather than a new rule-ID cluster, since it is a direct addition to the existing validation-methodology numbering, not a distinct new concept family the way Interaction Cycle & Gulfs was.

**Why this one process-shaped item is *not* excluded like the book's other process content.** Every other process item in this book (and in prior passes' sources) describes how a UX team runs research, design, or reporting work upstream of what `review` evaluates. The Cognitive-Walkthrough/Heuristic-Evaluation sequence is different in kind: it describes how an *expert review* — the literal activity `review`'s six skills perform — should itself be sequenced. It is scoped narrowly to a *structural ordering* addition (walk the primary task first, from a stated persona, before or alongside the existing rule-based sweep) rather than importing any new evaluative criteria, keeping it consistent with `review-model.md`'s existing self-referential scope (lens selection, synthesis, `V01`-`V06`) instead of expanding what review "reasons about" beyond that.

**Citation-only enrichments to `C05` and `L07` are not modeled as spec deltas.** Per `openspec/config.yaml`'s specs rule and this project's own proposal-writing convention ("Modified Capabilities... Only include if spec-level behavior changes"), adding a Sources-column citation to an existing rule's `Sources` field changes attribution, not the rule's `SHALL` behavior or any scenario — the existing `ux-crux/product` and `ux-crux/usability` requirements already describe the behavior unchanged. This mirrors the 0.1.6 pass's citation-only enrichment of `R06R`, which likewise required no spec delta.

## Risks / Trade-offs

- **Risk:** `N20R`'s "could a user plausibly place this under either category" test is inherently judgment-based and could be over-applied to any navigation with even minor conceptual overlap. → **Mitigation:** the requirement's scenarios anchor the finding to items that *actually* appear to belong under either category in the evidence (shared items, not merely similar-sounding labels), and the passing scenario requires clearly separated scopes, not zero conceptual proximity.
- **Risk:** `D08`'s dynamic zero-count-hiding requirement may not be assessable from a static screenshot, since it requires observing filter *interaction* behavior, not just a single filtered state. → **Mitigation:** consistent with this project's evidence model, a static single-state screenshot should be scored `NOT ASSESSABLE` or `LIKELY` for the dynamic-hiding half of `D08` while the one-click-clear-all half can often be verified `VERIFIED`/`SUPPORTED` from the same screenshot if a clear-all control is visibly present or absent.
- **Risk:** `F24` could be read as requiring every mobile form to add camera/geolocation/payment-sheet integrations regardless of relevance. → **Mitigation:** the requirement and its scenarios scope the flag to fields where the platform *already* provides a relevant capability and privacy permits its use; a field with no applicable device capability is explicitly a non-finding, not a gap to invent.
- **Risk:** `V07`'s walkthrough-first sequencing could be applied mechanically even when the evidence gives no real basis for a persona, leading to a fabricated or generic "first-time user" walkthrough that adds noise rather than insight. → **Mitigation:** the requirement's "No persona or primary task can be inferred" scenario explicitly requires `NOT ASSESSABLE` reporting plus a statement of what context would resolve it, rather than inventing an unstated persona — consistent with `V05`'s existing "record uncertainty... instead of inventing a violation when product context is missing" principle.

## Migration Plan

Standard content-only release: implement the `src/skills/**`-adjacent changes, then run `npm run build && npm run sync-version && npm run validate` (this project's standing release gate) before considering the change complete. No runtime migration — this is static Markdown content shipped as Agent Skills; there is no data model or running service to migrate. Rollback, if ever needed, is a plain revert of the commit(s) plus a rebuild.
