## Context

See `proposal.md` — Why. This is this project's seventh named-source comparison pass (after White Hat UX, Writing Is Designing, eye-tracking research, Digital Minimalism, a UX-team-of-one practice book, and an earlier UX-psychology synthesis pass — see `CHANGELOG.md`). The source is Andrew Hinton's *Understanding Context: Environment, Language, and Information Architecture*, an information-architecture and context-design book whose extracted item set was compared item-by-item against every existing rule in `src/skills/*/references/*.md` before this proposal was drafted, to avoid duplicating `A09R` (control-effect mismatch), `O13` (identity/demographic fields), `N16R` (breadcrumbs), `F17` (persistent cross-step form memory), and `PA09`/`PA11` (banner blindness / disguised ads), all of which already cover closely related failure modes surfaced elsewhere in the book.

## Goals / Non-Goals

**Goals:**
- Give `product`'s information-architecture check the depth its current two-rule state doesn't have, using Hinton's book plus the named theorists it surfaces (Dan Klyn, S.R. Ranganathan, Abby Covert) as independently citable sources.
- Add the small number of genuinely distinct, checkable rules the book contributes to `usability`, `trust`, and `psychology` that no existing rule already covers.
- Keep every addition mapped to one of the four existing skills touched — no new skill, no new top-level lens.

**Non-Goals:**
- Importing the book's process/methodology content (Applied Ethnography/Contextual Design, persona and journey-map critique, bubble-diagram/floor-plan facilitation technique) — this describes how a design team should work, not what a static-evidence review checks, consistent with every prior comparison pass's treatment of process content.
- Importing pure theory without a checkable anti-pattern (Umwelt, embodied cognition, Peircean semiotics as a taxonomy, berrypicking as a standalone theory) — kept only where the book itself supplies a concrete, testable failure mode (search-context preservation is the one piece of the foraging/berrypicking material that clears that bar).
- Physical-world-only cases that don't generalize to a digital product review (Norman doors, gas pump interfaces, elevator keypads).
- A new "context" or "information architecture" seventh skill. The IA content grows inside `product` as its own reference file, the same way `voice-tone.md` grew inside `product` for a different axis — not as a new top-level capability. This was raised as an open design question during exploration and the user chose to keep it inside existing skills.

## Decisions

**IA gets its own reference file, not a bigger `core.md`.** `product/references/information-architecture.md` is added, following the exact precedent of `voice-tone.md`: a reviewable axis distinct from Purpose/Task and Content gets its own file once it has enough independent conceptual weight (here: the Klyn materials framework, faceted classification, corporate-language friction, and the situation-need-task extension, on top of the existing `IA01`/`IA02`). `IA01`/`IA02` move out of `core.md` into the new file rather than being duplicated in both places. `product/SKILL.md`'s procedure step 4 and References section are updated to point at the new file, following the same pattern already used for `web.md` and `voice-tone.md`.

**Context-collapse and audience-scope content goes into `trust`, not `product`.** The dividing line used: `product` checks whether structure/labels match the user's mental model (findability); `trust` checks whether the system honestly discloses consequences and audience before an irreversible or consequential action. Facebook Beacon-style cross-audience broadcast defaults and Twitter-DM-fail-style audience-scope ambiguity are both "does the user know what will happen/who will see this before they commit" problems — the same shape as `trust`'s existing `E05`/`E07`/`E08` (confirmation-before-irreversible-action) and `O14`/`O15`/`CT01` (honest-default-disclosure) rules. This was an explicit open question during exploration, resolved with the user before this proposal was drafted.

**The Google Calendar merged-feed case (reified-label misalignment) stays in `product`, not `trust`.** Unlike the two rules above, this isn't a consent/disclosure failure — no one is broadcasting anything without permission. It's a structural/labeling clarity failure: one label conceals that it represents more than one underlying object with different visibility scopes. That's an IA/content-fidelity concern, so it becomes part of the new `Label-to-structure fidelity check` requirement in `product`'s IA file, alongside the unrelated-but-similarly-shaped metaphor-fidelity case (Camera Roll/Album containment).

**The situation-need-task (SNT) extension modifies the existing IA requirement, not the primary-goal requirement.** SNT is about how content and entry points are organized for users who haven't yet identified a task (an IA/findability concern — the same "structure organized around user mental models" principle IA01 already states, extended to situational rather than only goal-based mental models), not about single-screen visual hierarchy between a primary and secondary action, which is what the existing primary-goal-and-hierarchy requirement covers. Keeping SNT under IA avoids two requirements overlapping on the same evidence.

**Icon-reuse ambiguity is a new `usability` requirement, not a scenario on the existing control-truthfulness rule.** The existing rule (`A09R`) is about one control's own label/appearance not matching its own effect. The Zimbra case is different: two separate controls share the same signifier and each does exactly what a reasonable user would expect *for that control* — the failure is proximity and reuse, not any single control lying about itself. Distinct enough to warrant its own requirement rather than stretching `A09R`'s scenario set.

**Kuleshov-effect juxtaposition is a new `psychology` requirement, not folded into `PA09`/`PA11`.** Both existing rules are about an element being visually mistaken for something else (an ad mistaken for content, or vice versa). Unintended juxtaposition is a meaning-collision problem even when both elements are correctly identified for what they are (a promotional banner is clearly a promotional banner; the problem is what it means to see it next to a tragic headline). Different mechanism, different rule.

## Risks / Trade-offs

- **Risk:** Moving `IA01`/`IA02` out of `core.md` is a file-location change to existing, already-shipped rule content, not just an addition. → **Mitigation:** IDs stay the same (`IA01`/`IA02`); only the file changes. `product/SKILL.md` is updated in the same change so no reference is left pointing at the old location, and `scripts/validate.mjs`'s existing drift/reference checks will catch any stale pointer if one is missed.
- **Risk:** The new IA file could grow into a dumping ground for anything IA-flavored across future passes, diluting the "each rule ID owns exactly one destination file" invariant. → **Mitigation:** this pass documents the specific dividing lines used (structure/findability → `product`/IA; consent/disclosure → `trust`) in this design doc, for future passes to reuse rather than re-litigate.
- **Risk:** Expanding a requirement (`Information architecture check`) with several new scenarios in one MODIFIED block makes the delta large and harder to review than several small ADDED requirements. → **Mitigation:** the four new IA concerns (materials framework, faceted classification, corporate-language friction, situational entry points) all genuinely extend the same existing requirement's subject (how IA structure serves user mental models) rather than introducing an unrelated concern, so keeping them as one requirement with distinct scenarios is more accurate than splintering into four requirements that would all cite the same evidence and overlap at review time.

## Migration Plan

Standard content-only release: implement the `src/skills/**` and `src/shared/**`-adjacent changes, then run `npm run build && npm run sync-version && npm run validate` (this project's standing release gate) before considering the change complete. No runtime migration — this is static Markdown content shipped as Agent Skills; there is no data model or running service to migrate. Rollback, if ever needed, is a plain revert of the commit(s) plus a rebuild.
