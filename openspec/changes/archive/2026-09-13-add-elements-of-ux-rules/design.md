## Context

See `proposal.md` — Why. This is this project's eighth named-source comparison pass (after Writing Is Designing, eye-tracking research, Digital Minimalism, a UX-team-of-one practice book, White Hat UX, and Understanding Context — see `CHANGELOG.md`). The source is Jesse James Garrett's *The Elements of User Experience: User-Centered Design for the Web and Beyond* (2nd ed.), whose extracted 30-item knowledge map was compared item-by-item against every existing rule in `src/skills/*/references/*.md` before this proposal was drafted, to avoid duplicating `IE06` (interaction cost measured as total effort, not click count — the book's "meaningful steps over clicks-to-destination" item), `P02`/`P04`/`A01R` (primary-task hierarchy and progressive disclosure — the book's "primary task vs. edge-case equality" item), `P07` (first-use/repeat/expert-use distinction — the book's "audience segmentation" item), `IA01`/`IA04` (mental-model and organizational-leak checks — the book's "form follows psychology" item), and the distributed error-handling rules `E01`-`E04`/`A04R`/`A05R` (the book's four-layer error-handling framework, already covered across Prevention/Difficulty/Help/Recovery).

## Goals / Non-Goals

**Goals:**
- Add the specific, checkable, independently-namable rules the book contributes to `product`'s information-architecture and content checks, and to `usability`'s forms and navigation checks, that no existing rule already covers.
- Give the book's "Surface plane" (deliberate visual contrast, grid-based layout consistency) a home, since this is a structural gap in the existing catalog rather than a duplicate-content issue — the current catalog has no dedicated visual-hierarchy rules, only scattered eye-tracking citations in `usability`/`product`.
- Keep every addition mapped to the two existing skills touched (`product`, `usability`) — no new skill, no new top-level lens; this was raised as an open design question during exploration and the user chose to add a new reference file inside `usability` rather than a seventh skill.

**Non-Goals:**
- Importing the book's process/governance content (the Five Planes' bottom-to-top project-management dependency, Featuritis as a business-strategy warning, falsifiable-requirements as a spec-writing standard for PMs/BAs, the three pathological design-decision scenarios as an org-culture critique, the User Acceptance Testing timing trap, Marathon-vs-Sprint project pacing) — these describe how a design/product team should plan and govern work, not what a static-evidence review checks, consistent with every prior comparison pass's treatment of process content.
- Importing content that duplicates an existing rule's mechanism rather than adding a new one (ROI/conversion metrics as a business case for UX investment; audience segmentation, already `P07`; contextual inquiry/task analysis and cross-functional brainstorming as research/requirements-gathering methodology; wireframe documentation and cross-role collaboration as a team-process concern; tactile/auditory hardware feedback, already substantially covered by `usability`'s `S01`/`S02` perceivable-feedback rules for the digital-product surface this project reviews).
- A new "visual-design" or "surface" seventh skill. The visual-hierarchy content grows inside `usability` as its own reference file, the same way `information-architecture.md` and `voice-tone.md` grew inside `product` for their own axes — not as a new top-level capability. This was an explicit open question during exploration, resolved with the user before this proposal was drafted.

## Decisions

**Visual hierarchy gets its own reference file inside `usability`, not a bigger `core.md`.** `usability/references/visual-hierarchy.md` is added, following the exact precedent of `information-architecture.md` and `voice-tone.md`: a reviewable axis distinct from the existing Actions/Forms/Navigation/Interaction-efficiency sections gets its own file once it has independent conceptual weight (here: deliberate-contrast and grid-consistency rules, plus the squint-test technique). `usability/SKILL.md`'s procedure and References section are updated to point at the new file, following the same pattern already used for `mobile.md`.

**IA topology selection, controlled vocabulary, and conceptual-model consistency extend `information-architecture.md` as new rules (`IA06`-`IA08`), not new scenarios folded into `IA01`/`IA03`/`IA05`.** Each is a distinct enough mechanism to warrant its own rule ID: `IA06` (topology selection) is about which structural shape to use at all, a decision `IA01`'s mental-model check doesn't address; `IA07` (thesaurus/audience-facet fit) is about search-term mapping and audience-appropriate facet selection, which `IA03`'s faceted-classification-exists-or-not check doesn't address; `IA08` (conceptual-model consistency and literal-metaphor limits) is about a model's consistent application across the whole product and the cost of importing physical constraints, distinct from `IA05`'s narrower single-metaphor containment-fidelity and reified-label-merging scope. Keeping them as separate IDs (rather than stretching `IA01`/`IA03`/`IA05`'s existing scenario sets) preserves the one-rule-ID-to-one-mechanism clarity established in prior passes.

**The FAQ/format-vs-purpose trap becomes a new scenario on the existing `Content clarity check` requirement (`C18`), not a new requirement.** It shares the same underlying concern as `C01`-`C06`/`C13`-`C16` (does the content actually serve the user, evaluated on real evidence rather than internal assumption) and the same evidence/reporting shape, so it fits as an additional scenario on the same requirement rather than fragmenting content-quality checks across two requirements that would both cite similar evidence.

**Radio/checkbox-vs-dropdown (`F20`), default-option optimization (`F21`), and field-grouping micro-IA (`F22`) become their own requirements, matching this project's established one-requirement-per-rule pattern for its newer additions** (see `N15R`-`N18R`, `A11R`-`A12R` in the main `ux-crux/usability` spec, each its own requirement) rather than being folded into the broader legacy `State-completeness check`/`Task and interaction-efficiency evaluation` requirements that predate this per-rule granularity.

**Contextual inline navigation links (`N18R`) becomes a new requirement, not a scenario on an existing navigation requirement.** The main `ux-crux/usability` spec currently has no single consolidated "Navigation" requirement to extend (its existing navigation-shaped requirements — post-authentication redirect, breadcrumbs/footer sitemap, cross-device scoping — are each their own narrow requirement); a new, equally narrow requirement for the missing contextual/inline tier keeps the same granularity rather than introducing a new precedent.

## Risks / Trade-offs

- **Risk:** Adding a sixth reference file to `usability` (`core.md`, `mobile.md`, plus the new `visual-hierarchy.md`) could fragment where a reviewer looks for a given concern. → **Mitigation:** `usability/SKILL.md`'s procedure and References section are updated in the same change to point at the new file explicitly, following the exact pattern already established for `mobile.md`, so no reference is left dangling or undiscoverable.
- **Risk:** `IA06`'s "matrix exceeds 3 dimensions" and "organic structure for transactional content" flags could be over-applied to any multi-filter catalog. → **Mitigation:** the rule and its scenarios are scoped to *independent* classification dimensions in a combined browsing structure, not filters in general, and the design intentionally keeps the threshold as a cognitive-limit heuristic (matching this project's existing Miller's-Law folk-rule-guard precedent for not over-applying a numeric heuristic).
- **Risk:** The new `visual-hierarchy.md` rules (`VH01`/`VH02`) are inherently more subjective (what counts as "deliberate" vs. "accidental" contrast) than most of this project's rules. → **Mitigation:** each rule's scenarios anchor the judgment to a concrete, checkable condition (a stated functional difference with no visual signal, or vice versa; a demonstrated inability of the current grid to accommodate needed content) rather than a general aesthetic taste call, consistent with this project's evidence-model requirement that findings be evidence-backed rather than opinion-based.
- **Risk:** Folding `C18` into the existing `Content clarity check` requirement makes that requirement's MODIFIED delta large (it must restate all existing scenarios). → **Mitigation:** this is the same trade-off already accepted for `Content clarity check`'s prior expansions (Writing Is Designing and White Hat UX passes); restating a requirement's full scenario set at archive time is the schema's documented mechanism for MODIFIED requirements, not an avoidable cost.

## Migration Plan

Standard content-only release: implement the `src/skills/**`-adjacent changes, then run `npm run build && npm run sync-version && npm run validate` (this project's standing release gate) before considering the change complete. No runtime migration — this is static Markdown content shipped as Agent Skills; there is no data model or running service to migrate. Rollback, if ever needed, is a plain revert of the commit(s) plus a rebuild.
