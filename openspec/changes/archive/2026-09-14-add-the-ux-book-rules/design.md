## Context

See `proposal.md` — Why. This is this project's ninth named-source comparison pass (after Writing Is Designing, eye-tracking research, Digital Minimalism, a UX-team-of-one practice book, White Hat UX, Understanding Context, The Elements of User Experience, and Laws of UX — see `CHANGELOG.md`). The source is Rex Hartson & Pardha Pyla's *The UX Book: Agile UX Design for a Quality User Experience* (2nd ed.), whose extracted 28-item knowledge map (plus its process/methodology chapters) was compared item-by-item against every existing rule in `src/skills/*/references/*.md` before this proposal was drafted, to avoid duplicating Recognition over Recall (`PC02`/`F18`), Precise Wording (`A02R`), avoiding unnecessary modes / "UX karate" (`A11R` — the same Raskin/Norman quasimode research this project already cites), basic Fitts's-Law target sizing (`accessibility` `T01`/`T02`), and ego-free/constructive error messages (`E02`/`E03`).

## Goals / Non-Goals

**Goals:**
- Add the specific, checkable, independently-namable rules the book contributes that no existing rule already covers: effort-threshold discoverability, button-label/destination-header matching, an explicit disabled-control-explains-itself requirement, a high-handed-automation guard, generalized feedback-placement, decorative-clutter avoidance, destructive-control spacing, and chunked-number formatting.
- Give Hartson's Four Kinds of Affordances (Cognitive/Physical/Sensory/Functional) a diagnostic home inside `usability`, since this is a structural gap — the catalog already flags individual affordance-failure symptoms (`A08R`, `A09R`, `A12R`, `accessibility` contrast/size rules) but has no framework tying them to a shared vocabulary for *why* a control-level defect occurred, and no rule treating user-added physical workarounds (taped notes, cheat-sheets) as first-class diagnostic evidence.
- Give the Interaction Cycle / Gulf of Execution-Evaluation model a root-cause-classification home inside `review/references/review-model.md`, alongside the existing `V01`-`V06` validation methodology, so a reported breakdown states which stage it originates in instead of a generic complaint.
- Give Slanty Design a home inside `psychology/references/ethics.md` as a named, legitimate friction category distinct from a dark pattern, since the existing four-gate test and `trust` `E08` do not currently distinguish "friction that protects a shared resource/third party" from "friction that extracts a business advantage from the acting user."
- Keep every addition mapped to the three existing skills touched (`usability`, `review`, `psychology`) — no new skill, no new top-level lens.

**Non-Goals:**
- Importing the book's process/methodology content — Contextual Inquiry and the "three questions never to ask users," the System Complexity Space, syllogistic requirements extraction, Design-Informing Models, personas-as-focus-anchors, the Three HCI Paradigms, Agile UX / Sprint Zero integration, the RITE method, and the Ripple Model / architectural-support-for-usability material. These describe how a UX team researches, plans, and organizes its own process, not what a static-evidence review checks, consistent with every prior comparison pass's treatment of process content (see the Elements-of-UX and Understanding Context passes' identical treatment of their sources' process chapters).
- Re-deriving rules already covered under different names: Recognition over Recall, Precise Wording, mode/quasimode handling, basic Fitts target sizing, and ego-free error messages are confirmed already covered and left untouched.
- A new "affordances" or "interaction-theory" seventh skill. The Four Kinds of Affordances framework grows inside `usability` as its own reference file, the same way `information-architecture.md` and `voice-tone.md` grew inside `product`, and `visual-hierarchy.md` grew inside `usability` itself in the prior comparison pass — not as a new top-level capability.
- Reworking `ethics.md`'s existing four-gate test structure. Slanty Design is added as an additional named meta-rule (`PX05`) and a new row in the evidence-strength corrections table, not a restructuring of the four gates themselves.

## Decisions

**The Four Kinds of Affordances gets its own reference file inside `usability`, not folded into `core.md`.** `usability/references/affordances.md` is added, following the exact precedent of `visual-hierarchy.md` (added in the prior Elements-of-UX pass) and `information-architecture.md`/`voice-tone.md` in `product`: a reviewable diagnostic axis distinct from the existing Actions/Forms/Navigation/System-status sections earns its own file once it has independent conceptual weight — here, a cross-cutting classification framework (Cognitive/Physical/Sensory/Functional) that applies across many existing rules rather than living inside any one of them. `usability/SKILL.md`'s procedure and References section are updated to point at the new file, following the same pattern already used for `mobile.md` and `visual-hierarchy.md`.

**`affordances.md` explicitly cross-references existing rules rather than re-deriving them.** The false-cognitive-affordance anti-pattern (a control whose appearance promises behavior it doesn't have) is the same underlying concern as the existing `A09R` (control's actual effect must match its label/appearance); `affordances.md` names this explicitly as "the same concern as `A09R`, restated in affordance-type vocabulary" rather than creating a duplicate rule ID, preserving the project's one-rule-ID-to-one-mechanism invariant. `AF01`'s framework is the new content: a required diagnostic step (classify *which* affordance type failed) applied when writing up a control-level finding, not a new symptom-level rule competing with `A08R`/`A09R`/`A12R`.

**User-created affordances (`AF02`) is a new, standalone rule, not folded into `AF01`.** `AF01` is a diagnostic technique applied to a finding already made; `AF02` is itself a distinct evidence-gathering rule — it tells the reviewer what to do when it *sees* a specific kind of artifact (a taped note, a cheat-sheet) in the provided evidence, and what evidence-model status that artifact justifies. Keeping it as its own rule ID matches this project's established one-rule-ID-to-one-mechanism pattern (see `N15R`-`N18R`, `VH01`-`VH02` in the prior two passes, each its own requirement) rather than conflating a classification framework with an observational-evidence rule.

**Interaction Cycle & Gulfs (`IC01`) lands in `review/references/review-model.md`, not `usability/references/core.md`.** This is a cross-lens root-cause taxonomy that applies to any breakdown any domain skill might flag (a usability issue, an accessibility issue, a trust issue), the same reasoning that already put `V01`-`V06`'s validation methodology and the lens-selection/synthesis procedure in `review-model.md` rather than duplicating it inside each domain skill. Framing it as a new `IC` rule-ID cluster (rather than folding it into `V01`-`V06`) keeps the two concept groups — validation methodology vs. root-cause classification — separately namable, matching how `review-model.md` already keeps its Validation methodology and Lens-selection procedure as separate labeled sections rather than one undifferentiated rule list.

**Slanty Design (`PX05`) lands in `psychology/references/ethics.md`, not `trust`.** Although Slanty Design is about friction (a `trust`-adjacent concern), its defining question — "does this friction serve the user, a third party, or the business alone?" — is precisely the ethical-classification judgment `ethics.md`'s four-gate test and evidence-strength-corrections table already perform for every other persuasive/friction mechanism in this project. Placing it in `trust`'s `references/core.md` next to `E08` would duplicate the ethical-classification logic `ethics.md` already owns; placing it in `ethics.md` and cross-referencing `E08` (which the rule text does explicitly) keeps ethical-classification logic in one place, consistent with `ethics.md`'s stated role as "the meta-layer that keeps this skill from turning a descriptive psychological fact into a manipulative recommendation."

**The remaining seven rules (`N19R`, `A13R`, `A14R`, `IE14`, `S11`, `A16R`, `F23`, `VH03`) each become their own requirement/rule ID, matching this project's established one-requirement-per-rule pattern for newer additions**, rather than being folded into broader legacy requirements that predate this per-rule granularity (see `N15R`-`N18R`, `A11R`-`A12R`, `F20`-`F22` in the prior two passes, each its own requirement).

**`S11` generalizes `F07` rather than replacing it.** `F07` remains the form-specific validation-error-placement rule (WCAG-sourced, Accessibility evidence tier); `S11` is deliberately scoped to *non-form* feedback (status, confirmation, generic error) so the two rules do not overlap in scenarios — a form-validation-error finding stays under `F07`, while a generic action-confirmation or backend-error finding not tied to a specific form field falls under `S11`.

**`A16R`'s spacing concern is additive to, not a replacement for, `accessibility`'s `T01`/`T02` size contracts.** `T01`/`T02` govern a single target's own minimum dimensions; `A16R` governs the physical separation between two *different*, adjacent controls of unequal consequence. A control can pass `T01`/`T02` (individually large enough) while still failing `A16R` (too close to a destructive neighbor), so both are checked independently rather than treating size compliance as sufficient.

## Risks / Trade-offs

- **Risk:** Adding a fourth reference file to `usability` (`core.md`, `mobile.md`, `visual-hierarchy.md`, plus the new `affordances.md`) could further fragment where a reviewer looks for a given concern. → **Mitigation:** `usability/SKILL.md`'s procedure and References section are updated in the same change to point at the new file explicitly, following the exact pattern already established for `mobile.md` and `visual-hierarchy.md`, so no reference is left dangling or undiscoverable; `affordances.md`'s own text explicitly cross-references `core.md`'s `A08R`/`A09R`/`A12R` and `accessibility`'s `X02`/`X03`/`T01`/`T02` rather than existing in isolation.
- **Risk:** `AF02` (user-created affordances as a `VERIFIED`-leaning signal) could be over-applied — treating any user sticky note as automatic proof of a design defect regardless of context. → **Mitigation:** the rule's scenarios anchor the judgment to a concrete artifact actually visible in the evidence, and the requirement explicitly states that absence of such artifacts is not itself evidence of the opposite (no proof-by-absence), keeping the rule as an evidence-in interpretation aid rather than a license to speculate about workarounds not shown.
- **Risk:** `IC01`'s Translation-stage-first bias, if applied mechanically, could cause a reviewer to under-credit a genuine backend/Outcome-stage bug by defaulting to "the label was probably just unclear." → **Mitigation:** the rule's scenarios require the classification to be grounded in what the evidence actually shows (a user's hesitation/wrong-selection pattern vs. a confirmed state-change failure), and the "Reviewer initially suspects a backend defect" scenario is framed as reconsidering an *unsupported* Outcome-stage assumption, not overriding evidence that already confirms one.
- **Risk:** `PX05` (Slanty Design) could become a loophole excusing dark patterns by relabeling business-serving friction as "protecting a shared resource." → **Mitigation:** the requirement's own scenarios require the friction's primary beneficiary to be a third party or shared resource, not the business at the acting user's expense, and an unclear case is required to report `NOT ASSESSABLE`/`RISK` rather than defaulting to the legitimizing classification — mirroring this project's existing evidence-model discipline of choosing the weaker status under uncertainty.

## Migration Plan

Standard content-only release: implement the `src/skills/**`-adjacent changes, then run `npm run build && npm run sync-version && npm run validate` (this project's standing release gate) before considering the change complete. No runtime migration — this is static Markdown content shipped as Agent Skills; there is no data model or running service to migrate. Rollback, if ever needed, is a plain revert of the commit(s) plus a rebuild.
