# Review model: lens selection, synthesis, and validation methodology

This file is the only place the `review` skill's own logic lives beyond its `SKILL.md`. It does not duplicate the shared evidence, severity, or report models — see `../shared/evidence-model.md`, `severity-model.md`, and `report-contract.md`, which every skill (including this one) uses identically.

It covers rules V01-V06 (validation methodology) from the source catalog, plus the procedure for selecting which lenses apply and combining their output.

## Validation methodology (V01-V06)

| ID | Rule | Evidence | Default severity | Sources |
|---|---|---|---|---|
| V01 | Heuristic review is prevalidation, not proof of usability; critical flows still require observation with representative users. This caution applies with particular force to user testing conducted on a polished, high-fidelity mock-up: the Aesthetic-Usability Effect means users perceive a visually pleasing design as more usable and tend to overlook or under-report minor structural navigation flaws when testing it. Positive feedback on a high-fidelity mock-up's look-and-feel is not proof its underlying navigation/structure is free of defects — structural navigation mechanics should be validated on low-fidelity wireframes, before visual polish is applied, whenever testing has so far been conducted only on high-fidelity assets. | Research principle | Major | ISO 9241-210; NN/g Ten Usability Heuristics; Mark Wells, *User Experience Design* (Aesthetic-Usability Effect) |
| V02 | For each core flow, measure task success, error/recovery, time/effort, and qualitative confidence/satisfaction. When recommending a qualitative usability-test sample size, cite Jakob Nielsen's finding that ~5 participants surfaces the large majority of usability issues, including his 2012 revisit confirming that testing meaningfully more participants does not yield appreciably more insight — not an uncited or arbitrary number. When advising on how many participants must exhibit the same behavior before it is treated as a high-confidence pattern rather than an individual outlier, cite the convergence threshold of the same behavioral issue appearing in at least 6 of 8 participants across iterative testing cycles, rather than treating a single participant's behavior as sufficient grounds for a design change. | Research principle | Moderate | ISO 9241-210; Google Research HEART; Jakob Nielsen / NN/g, "Why You Only Need to Test with 5 Users" and its 2012 revisit; Mark Wells, *User Experience Design* (6-of-8 convergence threshold) |
| V03 | Use HEART selectively (Happiness, Engagement, Adoption, Retention, Task Success); do not optimize engagement when the product goal is rapid task completion. | Research principle | Moderate | Google Research, "Measuring the User Experience on a Large Scale" (HEART) |
| V04 | Test realistic adverse states: slow/offline network, denied permissions, empty data, server error, interrupted session, large text, dark mode, and small/large windows. Frame a dismissible-sounding "edge case" as a **stress case** when it corresponds to a real, non-negligible population or a genuinely stressful user circumstance, rather than treating rarity alone as license to exclude it — an unexamined business or technical constraint that excludes such a population (for example a sign-up form rejecting birth dates older than a fixed threshold with no stated legal or safety reason, which would exclude real centenarian users) is a finding to reconsider, not a scope boundary to accept by default. | Research principle | Major | ISO 9241-210; Apple HIG Accessibility; Android adaptive-layout guidance; David Hussman's "What-About" edge-case-probing technique, as cited in Jeff Patton with Peter Economy, *User Story Mapping* (the discovery-side counterpart to the same happy-path-blindness concern) |
| V05 | The reviewer records uncertainty and applicability instead of inventing a violation when product context is missing. | Skill architecture | Major | ISO 9241-210 |
| V06 | When a finding is reported `NOT ASSESSABLE` or `LIKELY`, name a concrete, low-cost technique to close the gap rather than stopping at stating uncertainty: a Five-Second Test for an unconfirmed information-hierarchy/first-impression claim, a Black Hat Session for a claim that depends on structured, candid team critique rather than end-user testing, the Role-Play UI Audit technique (below) for an uncertain claim about a flow's conversational quality or microcopy tone, or the Legacy Assumption Audit technique (below) when a requirement's only stated justification is precedent rather than a current need. | Research principle | Moderate | Christine Perfetti / User Interface Engineering (Five-Second Test); Edward de Bono, "Six Thinking Hats" (Black Hat Session); Anderson, *Seductive Interaction Design* (Role-Play UI Audit); Don Norman, *Design for a Better World* (Legacy Assumption Audit) |
| V07 | When a stated or reasonably inferable target persona and primary task exist for the reviewed evidence, walk through that primary task step-by-step from the target persona's perspective — a Cognitive Walkthrough evaluating step-by-step clarity, available system feedback, and whether progression is obvious — before or alongside applying the lens-selection procedure's Heuristic Evaluation sweep (the domain skills' rule-based checks). This is a structural sequencing addition, not a replacement for V01-V06 or the lens-selection/synthesis procedure, both of which apply unchanged. When no persona or primary task can be inferred from the evidence, report the walkthrough pass `NOT ASSESSABLE` and state what context would resolve it, rather than skipping the review or inventing an unstated persona. | Research principle | Moderate | Jesmond Allen & James Chudley, *Smashing UX Design* (Expert Review: Cognitive Walkthrough + Heuristic Evaluation hybrid) |
| V08 | An "MVP", beta, or early-access label on reviewed evidence does not exempt it from otherwise-applicable severity. Assess a finding's severity against whether the evidence achieves its stated target user or business outcome — Patton's Minimum Viable Solution definition — not against the effort a team saved by shipping a smaller release, and not by accepting the release-stage label itself as justification for a defect. | Research principle | Major | Jeff Patton with Peter Economy, *User Story Mapping* (Minimum Viable Solution vs. "crappiest product") |

### The Role-Play UI Audit (technique, not a separate rule)

To evaluate whether a flow's on-screen copy reads as a helpful, natural conversation rather than a robotic sequence of disconnected labels, run a two-person role-play: one person plays the user, speaking every thought and question out loud as they encounter the screen; the second person plays the interface, responding *only* with the exact form labels, button copy, and microcopy actually on screen — no paraphrasing, no filling in an implied but unwritten answer. Where the "interface" has no good answer to a natural question the "user" asked out loud, that gap is the finding: the on-screen copy failed to anticipate a question a real user would ask. This is the same kind of finding V06 already asks the reviewer to name a concrete technique for — use this one when the uncertainty is specifically about conversational quality or microcopy tone, not general information hierarchy (Five-Second Test) or team critique (Black Hat Session).

### The Legacy Assumption Audit (technique, not a separate rule)

To test whether a UI requirement or workflow step is a genuine current need or an obsolete administrative/procedural remnant, apply an iterative "why" probe when the only justification found in the evidence or accompanying context is "that's how it's always been done": ask why the requirement exists, then why the answer to that question is itself true, continuing until the chain either surfaces a real, current constraint (legal, safety, technical) or terminates in pure precedent with no current justification. A requirement that terminates in pure precedent is a candidate for elimination or redesign, not something to preserve out of caution — for example, a mandatory manual data-entry field in a clinical workflow that turns out to be an obsolete administrative remnant once its origin is traced (Norman's healthcare-data-entry case). This mirrors V06's pattern — use it when the uncertainty is specifically about *whether a requirement is still needed at all*, not information hierarchy (Five-Second Test), team critique (Black Hat Session), or conversational tone (Role-Play UI Audit). A designer does not need deep domain expertise to run this technique: naming and probing an unexamined assumption is itself the reviewer's job, distinct from the domain specialists who take the requirement for granted because they operate inside it daily.

These seven rules are why the `review` skill (and every domain skill) must say `NOT ASSESSABLE` or `LIKELY` rather than asserting a defect it cannot support (V05, tied directly to the evidence model); why a full review's output should point at what still needs a running build or real users (V01, V04) instead of presenting itself as a final verdict; why, once a finding is flagged uncertain, the reviewer names a specific, low-cost way to resolve it (V06) rather than leaving the uncertainty unaddressed; and why an expert review grounds its heuristic sweep in a concrete persona's task first whenever one is stated or inferable (V07), consistent with V05's "record uncertainty instead of inventing a violation when product context is missing" principle — a missing persona is reported as a gap, not silently invented, when V07's walkthrough pass cannot be run. V04's stress-case framing is why an adverse state should not be waved through as an acceptable exclusion merely because it looks rare — it may be a real population the current design silently locks out. V08 is why a release-stage label ("MVP", beta, early access) is never itself a defense against an otherwise-applicable finding — the same evidence-based severity assessment applies regardless of what stage the team calls the release.

## Interaction Cycle & Gulfs (root-cause classification)

A separate concern from V01-V06's validation methodology: once a breakdown has been observed, *where* in the interaction it originates determines what actually fixes it. Norman's stages-of-action model, via Hartson & Pyla, splits a single user action into five stages, grouped into two gulfs:

```
Gulf of Execution                              Gulf of Evaluation
  Planning -> Translation -> Physical Action -> Outcome -> Assessment
  (what?)     (how, on this  (doing it)          (system    (did it
               specific UI)                       state)     work?)
```

| ID | Rule | Evidence | Default severity | Sources |
|---|---|---|---|---|
| IC01 | When diagnosing the root cause of a usability breakdown, classify which Interaction Cycle stage it originates in — Planning (does the user know WHAT to do to reach their goal), Translation (does the user know HOW to do it on the specific UI objects in front of them), Physical Action (can the user physically perform it), Outcome (did the underlying system state actually change correctly), or Assessment (can the user perceive and confirm whether it worked) — rather than reporting a generic complaint. Because the large majority of real-world breakdowns occur at the Translation stage, consider a Translation-stage cause (ambiguous labeling, an unclear control-to-goal mapping) before concluding a breakdown is an Outcome-stage (backend/system) defect. | Research principle | Major | Hartson & Pyla, *The UX Book* (Norman's Stages-of-Action Model; Interaction Cycle & Gulfs) |

Classification must stay grounded in what the evidence actually shows: a user's hesitation or a wrong-selection pattern supports a Translation-stage finding, while a confirmed state-change failure supports an Outcome-stage finding. Do not use the Translation-stage bias to override evidence that already confirms a genuine backend defect — it exists to correct an *unsupported* assumption of one, not to relabel a confirmed one.

## Lens-selection procedure

The `review` skill does not run all five domain skills mechanically as a fixed pipeline. It reasons about which lenses are relevant to the evidence and request in front of it:

1. **Read the request and the evidence.** What is being reviewed (a screen, a flow, a feature spec, a running build)? What did the user ask for ("full review" vs. an implicit narrower ask like "does this feel trustworthy")? This is also where a target persona and primary task for V07's Cognitive Walkthrough pass are identified, if the request or evidence states or reasonably implies one — note explicitly when neither can be inferred, so V07 is reported `NOT ASSESSABLE` rather than silently skipped later.
2. **Default to broad coverage.** For an explicit "full review" or "review the UX of X" request with no narrowing, apply all five lenses (usability, psychology, accessibility, product, trust) unless one is clearly inapplicable to the evidence type (e.g. accessibility contrast checks are not assessable from a text-only description with no visuals — still name it as a lens considered and mark it `NOT ASSESSABLE`, do not silently skip it).
3. **Narrow only when the request narrows.** If the user's own request already scopes to one lens (e.g. "check accessibility"), invoke that domain skill directly instead — see "Independence from domain skills" below. `review` earns its place only for genuinely multi-lens or ambiguous-scope requests.
4. **State which lenses were applied and why**, as the first thing in the report, before the findings themselves.

## Independence from domain skills

Per the `ux-crux/review` spec's "Domain skills remain independently invocable" requirement: `review` is not a required dependency of `usability`, `psychology`, `accessibility`, `product`, or `trust`. Each of those five skills can run standalone and produce a complete report for its own lens, using the same shared evidence/severity/report models. `review`'s job is solely to decide *which* lenses apply to a broader request and to *synthesize* their findings into one report — it does not gatekeep access to any single lens.

## Self-containment

`review` does not read another skill's installed files, and does not assume the five domain skills are installed alongside it. Its own package carries a generated copy of every domain's reference content under `domains/<domain>/` (kept in sync with that domain's own `src/skills/<domain>/references/` by `scripts/build.mjs`). This matters specifically for skills.sh: `npx skills add <repo> --skill <name>` installs exactly one skill directory with no dependency mechanism, so a `review`-only install must be able to fully evaluate every lens on its own.

## Cross-lens synthesis

When multiple lenses produce findings on the same reviewed evidence:

1. Merge blockers and majors from every lens into one prioritized list (per `report-contract.md`) — do not present five separate mini-reports.
2. Where two lenses flag the same underlying issue from different angles (e.g. usability's "no confirmation copy is specific" and trust's "destructive action safety"), merge them into a single finding that cites both lenses' `source_ids` rather than reporting it twice.
3. Category health is still reported per lens (see `report-contract.md`), even after merging duplicate findings, so the user can see which lens found what.
4. When lenses disagree in emphasis (for example psychology flags a completion-progress mechanism as potentially manipulative while product would otherwise praise its clarity), report both perspectives rather than silently resolving the tension — this is exactly the kind of trade-off `design.md`'s "prevention vs. interruption" and "simplicity vs. capability" conflict classes describe, and the reviewer's job is to surface it, not average it away.

## How the review skill should apply this file

Use the lens-selection procedure before reading any `domains/<lens>/` file in depth — decide scope first, then load only the references needed for the applicable lenses, consistent with progressive disclosure (do not load all five domains' full reference sets for a narrowly-scoped request). Apply V01-V07 as a standing constraint on every report this skill produces, regardless of which lenses were selected — V07 specifically means running (or reporting as `NOT ASSESSABLE`) a persona-driven Cognitive Walkthrough of the primary task before or alongside the Heuristic Evaluation sweep the lens-selection procedure otherwise performs. When stating the root cause of a breakdown (not merely that one exists), apply IC01 to name the Interaction Cycle stage it originates in, so the recommended fix targets the actual failing stage rather than a generic complaint.
