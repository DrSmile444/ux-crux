# Usability: task flow, interaction, forms, status, errors, search, efficiency

Platform-agnostic. See `../shared/evidence-model.md` and `severity-model.md` for how to report findings from these rules. Platform-specific (iOS/Android) usability rules live in `mobile.md`.

## Actions

| A03R | Custom controls have visible pressed/active/disabled/selected states so interaction never feels ambiguous. | Strong | Major | Apple HIG Buttons, Feedback; NN/g Ten Usability Heuristics |

| A06R | Confirmation choices state outcomes instead of generic Yes/No where possible. | Strong | Moderate | NN/g Confirmation Dialogs; Apple HIG Writing |
| A07R | Alerts/dialogs are reserved for interruption-worthy information or a narrowly scoped task; low-priority feedback stays in context. | Strong | Major | Apple HIG Alerts, Modality, Feedback; Android Snackbar, Dialog |
| A08R | A control that appears interactive is actually interactive, and a disabled control is visually distinguishable and not the only explanation of unmet prerequisites. | Strong | Moderate | NN/g Ten Usability Heuristics; Apple HIG Feedback |

| A10R | A full-screen or otherwise fully blocking modal/overlay does not force an unrelated secondary action (e.g. disabling a content blocker, completing a survey) before the user can continue their original task; this is distinct from A07R, which governs when a dialog is warranted at all, not what it may demand once shown. | Strong | Major | Falbe, Frederiksen & Andersen, *White Hat UX* (Road Block pattern) |
| A11R | A persistent ("sticky") interaction mode — where the same gesture or control produces different results depending on a mode set earlier — is continuously and visibly indicated for as long as it is active; prefer a quasimode (a mode held only while a modifier is actively pressed, which reverts the instant it is released) over a silent sticky mode switch when the interaction allows it. | Strong | Major | Jef Raskin & Aza Raskin/Don Norman, mode-error and quasimode research |
| A12R | The same icon or visual signifier (for example a generic "X") is not reused for two different actions with materially different consequences when both appear close together in the same view; distinct from A09R, which addresses a single control's own label/effect mismatch, not one signifier meaning different things at different nearby locations. | Strong | Major | Andrew Hinton, *Understanding Context* (Zimbra icon-reuse case) |
| A13R | A button or link's label text matches, word-for-word, the heading of the screen or section it navigates to. Distinct from N07R, which addresses broader terminology/synonym consistency across a product, not a specific control's exact string matching its own destination's heading. | Strong | Moderate | Hartson & Pyla, *The UX Book* (terminology/label consistency) |
| A14R | A disabled/grayed-out control explains, when the user directly interacts with it (clicks, taps, or focuses it), why it is currently unavailable and what specific step would enable it; silent graying-out with no explanation on interaction is insufficient. Distinct from A08R, which requires only that a disabled control be visually distinguishable, not that it explain itself on interaction. A control a given user's permission level should never be able to use is hidden entirely rather than merely disabled. | Strong | Moderate | Hartson & Pyla, *The UX Book* (error prevention via disabling with explanation) |
| A16R | A destructive or high-consequence control keeps generous physical spacing from an adjacent safe, frequently used control of similar size, reducing the risk of accidental activation from motor overshoot — a Fitts's-Law-style movement-time concern about spacing between two different controls, distinct from `accessibility`'s T01/T02, which govern a single control's own minimum target size. | Strong | Moderate | Hartson & Pyla, *The UX Book* (Fitts' Law target ergonomics); Paul Fitts, "The Information Capacity of the Human Motor System" (1954) |

### Confirmation-dialogue simplification technique

When an A05R or A06R finding flags a confirmation dialog whose title, body copy, and button labels are misaligned, apply this refinement sequence rather than editing the wording ad hoc:

1. **Extract the discrete facts** the dialog currently states (what will happen, what conditions apply, what is reversible or not).
2. **Prioritize destructive/irreversible consequences first** — move the most consequential fact to the top; secondary details follow.
3. **Phrase the title as a direct question** rather than a statement or label (for example "Limit sharing to domain users?" instead of "Sharing settings").
4. **Align the button labels to literally answer that question** (for example "Yes"/"No") instead of generic or jargon verbs ("Enable"/"Cancel") that do not restate the question's answer.
5. **Strip jargon and redundant technical explanation** the buttons or title already made clear.

This is a technique for satisfying A05R (specific, consequence-naming confirmation) and A06R (outcome-stating choices), not a separate rule competing with them — a dialog can fail A05R/A06R without this sequence being the right fix (for example if the real problem is that no confirmation was needed at all, per A04R).

| F11 | Password creation requirements are disclosed before submission; users can reveal the entered password when appropriate. | Strong | Moderate | NN/g Checklist for Registration and Login |
| F12 | Form layout remains understandable with the software keyboard open and at large text sizes. | Strong | Major | Baymard mobile checkout forms; Apple HIG Accessibility; Android Grids and units |
| F13 | The primary action button (e.g. "Next"/"Submit") is aligned under the left edge of the input-field column; "Previous"/"Back" is placed to the left of "Next"/"Continue". | Strong | Moderate | Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design* (2014) |
| F14 | Field labels are positioned directly above their input box (top-aligned); if a label must be left-aligned instead, it is kept tight against the field rather than separated by wide whitespace. | Strong | Moderate | Matteo Penzo, "Label Placement in Forms" (UXmatters, 2006); Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design* (2014) |
| F15 | Illustration or example graphics placed next to an input field do not show realistic, copyable sample data (e.g. a legible sample ID number); obscure or abstract example content instead. | Strong | Moderate | Baymard checkout/form design research; Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design* (2014) |
| F16 | Distinct questions are arranged in a single vertical column, never side-by-side in separate columns, since users routinely miss an entire column of questions; a double-banked (two-column) layout is reserved for grouping answer *choices* within one question, not for separate questions. | Strong | Major | Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design* (2014) |
| F17 | Multi-step forms show previously entered key data (e.g. a selected date/time or location) as a persistent summary on later steps, rather than requiring the user to recall or navigate back to check it. | Strong | Moderate | Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design* (2014) |
| F18 | A selection control (dropdown, picker, or range slider) is not used for open-ended or high-cardinality data entry (e.g. building a full phone number one digit at a time from a dropdown); a text/numeric input with format guidance is used instead. A selection control remains correct for a small, genuinely constrained set (e.g. selecting a country or state from a validated list). | Strong | Major | Falbe, Frederiksen & Andersen, *White Hat UX* (Absurd Input Controls pattern) |
| F19 | Fields give immediate positive confirmation (e.g. an inline checkmark) as soon as valid input is entered or the field loses focus, not only error feedback after a failed submission. Distinct from F06/F07, which govern error/guidance content; this rule is about giving positive feedback on success, which those rules do not require. | Strong | Moderate | Falbe, Frederiksen & Andersen, *White Hat UX* (White Hat Form Optimization) |
| F20 | A small, fixed option set (fewer than roughly six choices) is shown as visible radio buttons (mutually exclusive) or checkboxes (independent) rather than hidden inside a collapsed dropdown, when screen space permits. Distinct from F18, which addresses open-ended/high-cardinality data unsuited to any selection control, not a small already-fixed set that should simply be shown. | Strong | Moderate | Jesse James Garrett, *The Elements of User Experience* (interface control selection trade-offs) |
| F21 | The statistically dominant/most common value for a high-frequency field or option is pre-selected by default when doing so carries no risk (e.g. "billing address same as shipping" checked by default); a system that can reasonably remember a user's previous choice across sessions reuses it rather than requiring re-selection every time. Distinct from F03, which addresses redundant entry within a single process, not defaults or cross-session memory. A high-risk financial, legal, or consent-bearing option is never pre-selected by this rule. | Strong | Moderate | Jesse James Garrett, *The Elements of User Experience* (default option optimization) |
| F22 | Related form/data fields are grouped into logical, meaningful sub-categories that reflect the user's mental model (e.g. Personal Info / Address / Contact), not alphabetical or arbitrary order. Distinct from F16, which addresses single-column visual layout of questions, not semantic grouping of fields. | Strong | Moderate | Jesse James Garrett, *The Elements of User Experience* (information design / content micro-IA) |
| F23 | A long numeric identifier a user must read, compare, or manually transcribe (a phone number, payment card number, or confirmation code) is displayed in visually chunked groups (e.g. "(555) 123-4567") rather than as a single unbroken digit string, reducing working-memory load during transcription or comparison; see `psychology`'s PC07 for the underlying chunking rationale. | Strong | Moderate | Hartson & Pyla, *The UX Book* (working memory limits and chunking) |
| F25 | A form does not require the user to manually supply or select data the system can already derive from other input already provided (e.g. a manual card-type dropdown when the card number's own digits already determine the type). Distinct from F03 (redundant entry of the *same* piece of information within one process) and F21 (defaults/cross-session memory of a *previously chosen* value) — F25 covers data that was never entered by the user at all but is mechanically derivable from something they did enter. | Strong | Moderate | Anderson, *Seductive Interaction Design* (smart-checkout/derived-field design) |

| ID | Rule | Evidence | Default severity | Sources |
|---|---|---|---|---|
| D01 | If search is a core task, it receives a primary, easy-to-find position rather than being buried. | Strong | Major | Apple HIG Searching |
| D02 | The current search scope is visible; users know what collection or section is being searched. | Strong | Moderate | Apple HIG Searching |
| D03 | Search reduces typing with useful suggestions, recent queries, completions, or corrections when privacy permits. | Strong | Moderate | Apple HIG Searching |
| D04 | No-results states distinguish "no data exists" from "filters/query excluded results" and offer meaningful recovery. | Strong | Moderate | NN/g Designing Empty States; Apple HIG Searching |

|---|---|---|---|---|

| R02R | If work cannot finish immediately, provide feedback before users interpret the UI as frozen. | Strong | Major | Apple HIG Loading, Feedback; Android Progress indicators; NN/g Website Response Times |

## Navigation (platform-agnostic principles)

Platform-specific navigation contracts (tab bars, back behavior, safe areas, foldables) are in `mobile.md`.

|---|---|---|---|---|
| N01R | Top-level destinations are few, stable, mutually meaningful, and consistently located. | Strong | Major | Apple HIG Tab bars; Android Layouts and navigation patterns, Navigation bar; NN/g Ten Usability Heuristics |
| N06R | Primary navigation is discoverable. Hiding high-frequency destinations behind an unlabeled menu requires a concrete reason. | Strong | Major | NN/g How to Make Navigation (Even a Hamburger) Discoverable on Mobile, Mobile UX Study Guide |
| N07R | Navigation labels use user language and stable terminology; identical concepts are not renamed across screens. | Strong | Moderate | NN/g Ten Usability Heuristics; Apple HIG Writing |
| N08R | Icon-only navigation/actions are limited to highly familiar symbols or supplemented with labels/accessibility names. | Strong | Moderate | Apple HIG Buttons, Gestures; Android accessibility principles |
| N09R | Hierarchy is not deeper than task complexity requires; users receive enough context to know where they are. | Strong | Moderate | NN/g Ten Usability Heuristics, Mobile UX Study Guide |
| N13R | Utility navigation (Contact, Help, Cart, Sign-in/Account) is placed in the standard top-right header or footer location; avoid sidebars or mid-page body placement, where users take much longer to find it. | Strong | Moderate | Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design* (2014) |
| N14R | Dynamic dropdown/mega-menu items are ordered by priority: the most critical items at the very top (1-2 positions), the next-most-critical at the bottom, and lower-priority items in the middle — matching the sweep-then-top-then-bottom-then-middle order users actually scan in, rather than a random or purely alphabetical order for short, non-alphabetic-lookup lists. | Strong | Moderate | Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design* (2014) |
| N15R | A post-login/post-authentication redirect returns the user to the exact screen, item, or step they were engaged with before authentication was triggered, rather than dropping them onto a generic homepage/dashboard. | Strong | Major | Falbe, Frederiksen & Andersen, *White Hat UX* (Wrong Destination pattern) |
| N16R | Deep-hierarchy sites provide a breadcrumb trail for orientation and a structured, multi-column footer sitemap; a simplified checkout or similarly streamlined flow may intentionally omit these as long as a clear exit/home path remains. | Strong | Moderate | Falbe, Frederiksen & Andersen, *White Hat UX* (Navigation Architecture Patterns) |
| N17R | A containment or scoping rule (for example, the default audience/group a new post is scoped to) established by the user's current context on one device or viewport carries over to another device or viewport of the same product, rather than silently resetting to a broader or different default. | Strong | Major | Andrew Hinton, *Understanding Context* (Google+ Circles cross-device scoping case) |
| N18R | Body/content text includes contextual inline hyperlinks to related items at the point of reading (for example a product description linking directly to a related accessory), rather than forcing the user back to a global or local menu to find related content. | N19R | A capability that technically exists but requires effort beyond a reasonable discovery/interaction threshold to reach (deeply nested menus, an undocumented gesture, or documentation-only discovery) is treated as effectively absent to users, distinct from N09R, which addresses hierarchy depth relative to task complexity rather than whether a specific capability is reachable at all without external help. | N21R | Navigation never uses an undifferentiated catch-all label ("Miscellaneous", "Resources", "More Info", "Other") as a dumping ground for content that does not fit the existing structure; the structure is expanded to accommodate the content with a specific, descriptive label instead. | Strong | Major | Jesmond Allen & James Chudley, *Smashing UX Design* (prohibition of catch-all navigation buckets) |

| ID | Rule | Evidence | Default severity | Sources |
|---|---|---|---|---|

| IE02 | Do not require a second tap merely to activate the input that was unambiguously requested by the previous tap. | Strong | Major | NN/g Interaction Cost, Direct Access vs. Sequential Access, EAS Framework |
| IE06 | Evaluate efficiency as total physical + cognitive effort, not click count alone. | Strong | Major | NN/g Interaction Cost; Don't Prioritize Efficiency Over Expectations |
| IE07 | Apply EAS in order: eliminate unnecessary work, automate deterministic/reversible work, then simplify what remains. | Strong | Moderate | NN/g Less Effort, More Completion (EAS Framework) |
| IE08 | Prefer direct access for frequent, independently useful destinations/actions instead of forcing users through serial intermediate states that add no value. | Strong | Moderate | NN/g Direct Access vs. Sequential Access |
| IE09 | Do not remove a familiar step if the resulting automation makes system state ambiguous or violates a strong mental model; preserve visible status/control. | Strong | Major | NN/g Don't Prioritize Efficiency Over Expectations; Ten Usability Heuristics |

## Folk-rule guards

These are the exact kinds of oversimplified rules a review is likely to hallucinate as absolutes unless explicitly constrained. Apply the "better encoding" instead of the folk rule.

| Folk rule | Better encoding |
|---|---|
| "Never use a hamburger menu." | Penalize hidden **primary/high-frequency** navigation when discoverability matters; allow it for secondary/large sets of destinations (see N06R). |
| "All primary actions must be at the bottom because of the thumb zone." | Consider reachability and frequency, but do not assume a single grip; thumb-zone reasoning is a heuristic, not a layout law (see `mobile.md` T07). |
| "Always show onboarding." | Default to no standalone onboarding; require it only when setup, unfamiliar mechanics, safety, or unavoidable conceptual complexity justify it (product-lens concern, see `product` skill). A modal instruction pop-up is a particularly weak substitute: an eye-tracking study of a tablet app found most users dismissed an instructional pop-up in well under a second of fixation, and all subsequently failed the custom-gesture task it was meant to teach (Romano Bergstrom & Schall (eds.), *Eye Tracking in User Experience Design*, 2014). |
| "Always confirm delete." | Prefer undo for routine reversible deletion (A04R); confirm serious, unusual, irreversible, expensive, or security-sensitive actions (A05R, and trust-lens destructive-action rules). |
| "Never use dialogs." | Use dialogs for truly interruptive, narrowly scoped tasks or critical decisions; avoid them for ordinary informational feedback (A07R). |
| "Always use a skeleton instead of a spinner." | Show useful structure/content early when it improves comprehension (S03); use determinate/indeterminate progress according to what is actually known (S04). |
| "Bottom navigation must always have exactly N items." | Use platform-specific guidance — see `mobile.md` N03R for Android's 3-5 destination target; iOS guidance focuses on top-level navigation semantics, not a fixed count. |
| "Disabled buttons are bad." | A disabled state can be valid, but prerequisites must be understandable and users must not be trapped without explanation (A08R). |
| "Swipe actions are bad." | Swipe can be an efficient shortcut for contextual actions, but must stay consistent, discoverable, and not the only access path to important functionality (see `mobile.md` T06). |
| "Animations are bad/good." | Motion must communicate state or continuity, remain responsive, and respect reduced-motion settings; decorative motion should not impede tasks. |
| "More steps are always worse." | A short staged flow can reduce complexity and errors; the cost depends on dependency between steps, frequency, and information needed for decisions (see `product` skill P03). |
| "Miller's Law means navigation/menus must cap out at 7 (or 5) visible items." | Miller's Law describes active working-memory retention (holding items in mind without looking), not recognition of options that stay visible on screen — it does not set a maximum count for always-visible navigation or menus. Apply semantic chunking instead (see `psychology` skill PC07), and only reduce the number of choices when decision complexity actually warrants it (Hick's Law, see this file's Actions/Forms sections and the `product` skill). |

## How the usability skill should apply these

Start from the primary task (handed off from, or checked alongside, the `product` lens), then work through state-completeness (System status, Errors & recovery — is every state in `evidence-model.md`'s sense actually shown or knowably absent?), then interaction efficiency (does every explicit user intent get continued without redundant taps?), then the folk-rule guard table before finalizing any finding that resembles a popular "always/never" rule. When the evidence includes a form, also check the layout-ergonomics rules (F13-F17: button alignment, label proximity, sample-data contamination, single-column question layout, cross-step memory), the control-type rules (F18: no dropdown/select misuse for open-ended, high-cardinality data; F20: no dropdown misuse the other direction — a small, already-fixed option set hidden when it should be shown as visible radio buttons/checkboxes), the positive-feedback rule (F19: immediate confirmation on valid input, not only errors on failure), the defaults/memory rule (F21: dominant-value pre-selection and cross-session choice memory), and the field-grouping rule (F22: logical mental-model grouping, not alphabetical order). When it includes navigation menus, a dropdown/mega-menu, a list of options to compare, a post-authentication redirect, a deep-hierarchy page, or body content that mentions a related item, check N13R-N18R and D06 alongside the rest of Navigation and Search/discovery — N15R (redirect returns to prior context), N16R (breadcrumbs/footer sitemap), and N18R (contextual inline links at the point of reading) are new alongside the existing set. Check every control's actual effect against its label/appearance (A09R), every blocking modal against whether it forces an unrelated secondary action (A10R), any persistent/sticky mode against whether it is continuously visible (A11R), and any reused icon/signifier near a different, higher-consequence action against A12R, as part of the Actions pass, alongside A01R-A08R. Also check whether a control's label matches its destination's own heading word-for-word (A13R), whether a disabled control explains itself when interacted with rather than staying silently grayed out (A14R), and whether a destructive control keeps adequate physical spacing from an adjacent safe control (A16R) — this is additive to `accessibility`'s T01/T02 target-size contracts, not a replacement for them. When the evidence shows a scoping or containment default (for example a post's audience) established on one device, also check N17R against its mobile/desktop or cross-viewport counterpart. When the evidence includes a navigation structure, also check N19R: is every capability actually reachable within a reasonable discovery/interaction threshold, or does reaching it require external documentation or excessive nested navigation? Check top-level categories against N20R (could a user plausibly place the same item under more than one category?) and N21R (does any label function as a vague catch-all dumping ground rather than a specific, descriptive category?) alongside the rest of Navigation. When the evidence includes a search or discovery flow, check D07 (query/context preservation across a non-linear session) and D08 (faceted filters prevent zero-result dead ends and offer a one-click clear-all control) alongside the rest of Search, discovery & comparison. When a list/collection view is evaluated, also check IE13 (bulk actions) and IE14 (background automation must not seize focus or interrupt active input) alongside the rest of Interaction efficiency. When the evidence shows any non-form status, confirmation, or error feedback, check S11 for focus-of-attention placement — F07 remains the rule for form-field validation feedback specifically. When the evidence includes a long numeric identifier the user must read or transcribe, check F23 for chunked formatting. When a form field asks the user to manually supply or select a value the system could instead derive from other input already given (e.g. a card-type selector alongside a card-number field), check F25. When a finding could be explained by either a genuine usability defect or a legitimate contextual exception (progressive disclosure, secondary navigation, a deliberately browse-first search state), report it with the appropriate `evidence-model.md` status and name the exception condition rather than asserting a defect outright. When an A05R/A06R finding involves a confirmation dialog whose title, body, and buttons are misaligned, recommend the Confirmation-dialogue simplification technique (in this file's Actions section) as the concrete fix rather than a generic "make this clearer" recommendation.
