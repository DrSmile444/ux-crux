# Usability: mobile platform contracts (iOS / Android)

Mobile-specific addendum to `core.md`. See `../../../shared/evidence-model.md` and `severity-model.md` for how to report findings from these rules. A web/desktop addendum may be added later without changing this file.

## Forms (platform contracts)

| ID | Rule | Evidence | Default severity | Sources |
|---|---|---|---|---|
| F24 | A mobile form field that maps to a device capability — camera-based document/card scanning, geolocation-based address autofill, or an OS-level payment sheet such as Apple Pay/Google Pay — uses that capability instead of requiring full manual entry, when the platform provides it and privacy permits. Distinct from `core.md`'s F04 (correct keyboard/input-mode/autocomplete configuration for manually-typed input, not replacing manual entry) and F10 (password-manager/non-memory authentication, scoped to authentication flows, not general form input). | Strong | Moderate | Jesmond Allen & James Chudley, *Smashing UX Design* (mobile distraction design and device-capability input) |

## Touch & ergonomics (gesture and thumb-zone heuristics)

Target size, spacing, and dragging-alternative requirements are accessibility concerns and live in the `accessibility` skill's references, not here.

| ID | Rule | Evidence | Default severity | Sources |
|---|---|---|---|---|
| T06 | Custom gestures are discoverable, consistent, and supplementary to standard interactions. | Strong | Major | Apple HIG Gestures; NN/g Using Swipe to Trigger Contextual Actions |
| T07 | Do not hard-code a universal "thumb zone". Reachability is considered, but layouts are tested with different grips, hands, device sizes, and contexts. | Contextual | Moderate | Microsoft Research Target Size Study for One-Handed Thumb Use; UXmatters How Do Users Really Hold Mobile Devices?; Apple HIG Designing for iOS |
| T08 | Frequent/high-value actions should not require precision at the screen edge where system gestures or grip changes increase error risk. | Strong | Moderate | Android system bars, Edge-to-edge design; Microsoft Research Target Size Study |
| T09 | Gesture-driven interactions provide immediate visual/haptic feedback proportional to the action. | Strong | Moderate | Apple HIG Gestures, Feedback |
| T10 | A carousel on a touch screen lets users reach its last item in a few swipes or taps, orders its items by priority, groups items that relate to each other so the first item predicts the rest, and does not hold content users must see, which is also reachable by another path. Distinct from PA20, which concerns auto-rotation and swipe control of a homepage carousel, not how many steps the carousel needs or whether its content is reachable elsewhere. Does not apply to a list view that lets users open any item directly; swipe behaviour that a static design does not show is `NOT ASSESSABLE`. | Strong | Moderate | Nielsen Norman Group, Budiu, "Carousels on Mobile Devices" (2018) |

### Worked example: Search reveals an unfocused input

**Scenario:** A user taps a Search control. The app reveals a text field, but the field is not focused and the software keyboard stays closed. The user must tap the field again to start typing.

**Assessment:** Usually a **major** usability finding (IE01-IE02 in `core.md`, IE03-IE05 here) when typing is clearly the dominant next action, at `SUPPORTED` or `LIKELY` evidence status depending on whether the evidence is a live interaction trace or a pair of static screenshots.

**Why:** The Search tap already expresses intent to enter a query. The second tap adds physical interaction cost and visual target-reacquisition for no safety or choice benefit. Android explicitly supports requesting keyboard focus in response to a user interaction (`FocusRequester`); Apple's own guidance is to avoid changing focus *without* user interaction — which is not violated here, since the original tap on Search *is* the user interaction that licenses the resulting focus change.

**Expected behavior:** After the Search transition completes, focus the revealed field and present the software keyboard (IE01, IE04). Keep the field and useful suggestions/results visible above the keyboard (IE05). Preserve the query when dismissing and restoring search where appropriate (IE10 in `core.md`).

**Exception:** If activating Search intentionally opens a browse-first surface — recent searches, categories, voice/image search, or suggestions where typing is not the dominant next step — automatic keyboard presentation can be wrong (IE12). Treat this exception as `RISK`/contextual and worth testing, not as proof the original finding was mistaken.

## How the usability skill should apply these

This file's rules split into two groups that require different platform resolution. **Genuinely native-only platform contracts** — N02R (iOS tab bar), N03R (Android `NavigationBar`), N04R (native back behavior), and T06-T09 (custom-gesture and thumb-zone ergonomics) — require an explicitly native iOS or Android platform to apply; do not apply them to web/hybrid evidence, and do not average iOS and Android guidance against each other. **Mobile-viewport-general rules** — L01 (safe-area/inset handling), L05 (dark/increased-contrast appearance), L07 (localization text-expansion), and L08 (scalable font units) — address concerns inherent to any mobile-viewport rendering, not a native-platform API, and apply to mobile web evidence just as much as to native apps (CSS `env(safe-area-inset-*)`, `prefers-color-scheme`, flexible-width containers, and `rem`/`em` units are the web-side equivalents). When the evidence is a mobile web page rather than a native app, do not skip this entire file — resolve which of its rules are native-only (skip those) versus viewport-general (still apply those) rather than treating "not native" as "mobile.md doesn't apply."

When the evidence includes a mobile form field that could be filled via a device capability (camera scanning, geolocation, an OS-level payment sheet), check F24 alongside `core.md`'s F04/F10 — F24 is about replacing manual entry entirely, not configuring the manual-entry experience itself. When a search/input-reveal pattern appears, run the worked-example check explicitly: was this transition user-initiated, and does typing follow as the obvious next step? If the evidence is a static screenshot pair, report the finding at `LIKELY` rather than `VERIFIED`, and name "a live interaction trace or the running build" as the validation method per the shared evidence model.

When the evidence shows an iOS sheet, check N25R; when it shows an iOS tab bar, check N26R beside N02R; when it shows a Dark Mode screen, check L09 beside L05. These three are iOS platform contracts and do not apply to Android evidence.

Baymard Institute research rules added in this file: F28, N27R, N28R, N29R, N30R. Check each when the evidence shows its surface (forms and checkout, navigation, search and filters, accounts and orders, delivery and returns); each reports `NOT ASSESSABLE` for parts the evidence does not show.

Nielsen Norman Group research rules added in this file: D34, D35, F48, L10, L11, L12, L13, L14, L15, N51R, N52R, N53R, N54R, T10. Check each when the evidence shows its surface; each reports `NOT ASSESSABLE` for parts the evidence does not show.
